# دليل إطلاق بُعد والتراجع الآمن

هذا الدليل هو بوابة إلزامية قبل فتح الموقع للعامة. لا تُرقّى نسخة إلى الإنتاج إذا بقي بند حرج غير مكتمل.

## 1. تجميد نسخة الإطلاق

- حدّد commit واحدًا على فرع `staging` بوصفه مرشح الإطلاق.
- أوقف تغييرات المحتوى والمخطط أثناء الاختبار النهائي.
- تأكد أن جميع فحوص GitHub ونشر Vercel للنسخة نفسها ناجحة.
- احتفظ بنسخة Vercel السابقة الجاهزة للعودة السريعة.

## 2. الفحص الآلي

شغّل من نسخة نظيفة وباستخدام Node.js 22 أو 24:

```bash
npm ci
npm audit --audit-level=low
npm run check
```

يجب أن تكون النتيجة:

- صفر ثغرات معروفة في تدقيق الاعتماديات وقت الفحص.
- نجاح الفحص الثابت وجميع الاختبارات والبناء.
- نجاح اختبار manifest وتطابق كل ترحيلات قاعدة البيانات.
- عدم وجود أخطاء تشغيل جديدة في سجلات Vercel.
- عدم وجود تحذيرات أمنية جديدة غير مفحوصة في Supabase.

## 3. اختبار القبول بحسابات حقيقية

نفّذ الاختبارات على بيئة التجربة من متصفح نظيف، مرة على الكمبيوتر ومرة على الجوال:

### زائر

- تصفح الصفحة الرئيسية والكتالوج والبحث والفلاتر والتحميل المتدرج.
- فتح منتج ومورد والتنقل ذهابًا وعودة.
- فتح عارض 3D، الدوران والتكبير والإيقاف وإعادة الضبط والإغلاق.
- التأكد من منع العمليات التي تتطلب تسجيل الدخول برسالة واضحة.

### مستخدم عادي

- إنشاء حساب، تأكيد البريد، تسجيل الدخول والخروج، واستعادة كلمة المرور.
- حفظ منتج داخل مشروع والتأكد من بقائه بعد إعادة تحميل الصفحة.
- تنزيل ملف تصميم حقيقي مصرح به والتأكد من نوع الملف واسمه وحجمه.
- التأكد من رفض الوصول إلى الإدارة والكتابة الإدارية.

### مدير

- إنشاء وتعديل ومراجعة ونشر ثم إخفاء منتج تجريبي مخصص للاختبار.
- رفع صورة وملف تصميم مصرح بهما ثم معاينتهما وتنزيلهما.
- تعديل مورد والتحقق من ظهور النتيجة في الواجهة العامة.
- التأكد من تسجيل العملية في سجل التدقيق وعدم كشف بيانات غير لازمة.

بعد الاختبار احذف محتوى الاختبار فقط بالطريقة الاعتيادية داخل الإدارة، ولا تحذف بيانات حقيقية أو تعِد ضبط قاعدة البيانات.

## 4. إعدادات الخدمة والأمان

- تفعيل حماية كلمات المرور المسرّبة في Supabase إن كانت الخطة المختارة تدعمها.
- اعتماد سياسة نسخ احتياطي واستعادة مجرّبة؛ حسم الحاجة إلى PITR قبل الإطلاق.
- ربط بريد تشغيلي موثوق للمصادقة واختبار التسليم ومعدل الإرسال والروابط.
- ضبط Site URL وقائمة Redirect URLs على النطاقات المعتمدة فقط.
- مراجعة مفاتيح البيئة في Vercel لكل من Preview وProduction، وعدم وجود `service_role` في الواجهة.
- إبقاء حماية بيئة التجربة، وتحديد سياسة حماية الإنتاج بقرار صريح.
- اعتماد النطاق وHTTPS وسياسة التحويل بين www والنطاق الأساسي.

## 5. المحتوى والالتزام

- إزالة المحتوى التجريبي أو وسمه بوضوح إذا كان مقصودًا.
- اعتماد المنتجات والموردين وبيانات التواصل من مالكي المحتوى.
- تأكيد حقوق استخدام الصور وملفات التصميم والنماذج ثلاثية الأبعاد.
- اعتماد سياسة الخصوصية والشروط وآلية البلاغ والحذف ومالك قناة الدعم.
- عدم نشر ملفات فارغة أو روابط تنزيل وهمية.

## 6. تسلسل الإطلاق

1. سجّل نتائج البنود السابقة واسم المنفذ ووقت الاختبار.
2. أنشئ نسخة احتياطية قابلة للاستعادة أو أكد آخر نسخة ناجحة وفق الخطة.
3. رقِّ commit المرشح نفسه من `staging` إلى الإنتاج؛ لا تبنِ من تغييرات إضافية غير مفحوصة.
4. نفّذ فحصًا سريعًا على النطاق العام: الصفحة، الكتالوج، المصادقة، منتج، مورد، 3D، وتنزيل حقيقي.
5. راقب أخطاء المتصفح، وظائف Vercel، المصادقة، وقاعدة البيانات لمدة 60 دقيقة على الأقل.
6. أبقِ قناة المسؤول التقني مفتوحة خلال نافذة المراقبة.

## 7. قرار التراجع

تراجع فورًا عند وجود تسريب بيانات، تجاوز صلاحيات، فشل مصادقة واسع، فساد بيانات، تعطل الكتالوج، أو ارتفاع مستمر في أخطاء الخادم.

1. أعد توجيه الإنتاج إلى آخر نشر Vercel سليم.
2. لا تستخدم `git reset --hard` ولا reset لقاعدة البيانات.
3. أوقف العملية المتسببة أو اخفِ الميزة إن أمكن دون إتلاف البيانات.
4. احتفظ بالسجلات والتوقيت ومعرّفات الطلبات للتحقيق.
5. أصلح قاعدة البيانات بترحيل أمامي جديد. استعادة النسخة الاحتياطية قرار طارئ يتطلب تقدير فقد البيانات منذ النسخة.
6. أعد جميع فحوص هذا الدليل قبل محاولة إطلاق جديدة.
